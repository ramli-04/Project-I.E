# Couverture du processus BPMN

État au 25 novembre 2026, étape UX 8.2 (capacité indicative et encaissements v1 vérifiés). Référence : transcription des deux pages du BPMN dans la section 1 de `AGENT_PROMPT_UX_STREAMLINING.md`. Le PDF original n’a pas été réinterprété. Les [diagrammes générés](WORKFLOW.md) décrivent le code actuel ; cette matrice compare ce code au processus demandé.

Les tableaux recensent les 37 éléments, dont les 10 passerelles, puis leurs 20 issues distinctes : **57 lignes BPMN**. G2 utilise les issues **Physique / Fichier STL**, et non Oui / Non. Les deux destinations « Fin » sont distinguées par leur branche clinique ou facturation ; ces suffixes servent uniquement à la lecture de la matrice. Les identifiants RG et D sont également des repères documentaires, pas de nouveaux éléments du BPMN.

Sur ces 57 lignes : **41 covered, 15 partial, 1 missing**. Ce sont des nombres de lignes, pas un pourcentage de fonctionnalités : la ligne manquante est la boucle d’attente E1, volontairement omise en v1 ; B8 est couvert dans le périmètre v1 approuvé, sans attestation d’envoi externe réel.

- **✅ covered** : comportement applicatif représenté et vérifié par les tests cités, dans le périmètre synthétique. Cela ne certifie ni un geste clinique réel ni un envoi externe.
- **⚠️ partial** : une partie existe, avec une différence ou une limite indiquée dans la correspondance et les divergences.
- **❌ missing** : le comportement BPMN n’existe pas. Une fonction voisine ou un test de parcours heureux ne suffit pas à le déclarer couvert.

La colonne manuelle est indépendante du statut automatisé. **MY-TEST-001** démontre uniquement le parcours heureux **physique → CFAO → design approuvé → cristallisation → livraison/PIN → essayage validé**, avec une ligne standard de **1500,00 MAD** dans le relevé de novembre. Elle ne prouve pas les exceptions, les autres routes, la clôture mensuelle, l’envoi de facture ou le paiement. Ne pas modifier ce dossier pour compléter cette matrice. Les essais automatisés utilisent une base jetable et les navigateurs réels un projet Docker séparé.

Les fichiers de tests cités sont dans [`cabinet_backend/api/`](../cabinet_backend/api/). Les références `fichier::test` désignent les méthodes réelles de ces modules ; une référence soutient uniquement la partie décrite, jamais une fonction signalée absente. Les critères sont sélectionnés explicitement dans les tests synthétiques : aucune approbation clinique automatique n’a été ajoutée.

## Vérification ajoutée en phase 7

Sept nouvelles méthodes de test exécutent les comportements existants sans modifier les services applicatifs : renvoi physique et nouvelle inspection de révision, recoulée/rescan avec pertes mesurées, corrections de design jusqu’à approbation de version suivante, reprise en fabrication, échec qualité vers trois postes possibles, contestations avant émission et avoir après émission. Le test de reprise après livraison vérifie aussi qu’un essayage échoué ne clôture pas le dossier ni ne crée une reprise implicitement.

Pour G10, les scénarios sont volontairement distincts : une ligne exclue avant clôture n’est jamais facturée et ne reçoit pas d’avoir ; une correction après émission produit un avoir plafonné et un PDF, conserve la facture immuable et ne produit pas de doublon. Un montant invalide annule toute la résolution ; le dentiste ne peut pas exécuter la résolution comptable. Une contestation rejetée rétablit l’inclusion avant clôture.

Les résultats datés, commandes, durées et limites sont dans [TEST_RESULTS.md](TEST_RESULTS.md). Le [guide de démonstration](../DEMO_GUIDE.md) décrit les clics réels. Cette matrice ne vaut pas validation de capacité en laboratoire, certification clinique, essai d’équipement connecté ou preuve d’envoi/paiement.
